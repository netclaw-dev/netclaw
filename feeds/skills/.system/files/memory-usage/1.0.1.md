# Memory Usage

<!-- description: SAVE user facts, decisions, and solutions to memory. RETRIEVE at conversation start before answering from scratch. -->

## Provider Routing

Netclaw supports two memory backends. Check `~/.netclaw/config/netclaw.json`
under `"Memory": { "Provider": "..." }` to determine which is active.

| Provider | Default? | Tools Available | Details |
|----------|----------|-----------------|---------|
| `files` | Yes | `search_memories`, `store_memory` (always loaded) | See **File-Backed Memory** below |
| `memorizer` | No | `search_memories`, `store_memory` (after MCP connects) | See `file_read` on the memorizer-usage skill |

Both providers expose the same two tool names. You do not need to know which
backend is active — just use `search_memories` and `store_memory`.

## Behavioral Triggers

**RETRIEVE** — At the start of each conversation, `search_memories` for topics
relevant to the user's first message. Also search when asked about something
you might have encountered before. Check before answering from scratch.

**SAVE** — When the user shares durable facts about themselves, their
environment, projects, or decisions, save immediately using `store_memory`.
Don't wait until end of conversation. Durable facts include:
- Their physical or cloud infrastructure (hardware, OS, network topology)
- Project context, goals, and constraints
- Preferences, workflows, and conventions they've established
- Decisions made and the rationale behind them
- Solutions to problems (especially non-obvious ones)
- Research findings that may be relevant in future conversations

## What to Save

- Solutions to problems (especially non-obvious ones)
- User-confirmed facts about their projects or environment
- Architectural decisions and their rationale
- Research findings that may be relevant later
- Troubleshooting steps that worked
- Project context and conventions discovered in codebases
- Personal environment facts (hardware, OS, network, homelab setup)
- Goals and ongoing initiatives the user is pursuing

## What NOT to Save

- Ephemeral task state (current work in progress, temporary context)
- Information already in identity files (SOUL.md, AGENTS.md, TOOLING.md)
- Unverified guesses or speculative conclusions
- Duplicate information — search first, then update or create new

## File-Backed Memory

This is the default provider (`"Provider": "files"` or unset).

### Tools

Both are always-loaded builtins — no discovery step required:

- **`search_memories`** — keyword search across all stored memories.
  Params: `Query` (required), `Limit` (optional, default 5).
- **`store_memory`** — create a new memory file.
  Params: `Title` (required), `Content` (required), `Tags` (optional,
  comma-separated).

### Storage Format

Memories are stored as individual markdown files with YAML front matter:

```
~/.netclaw/memories/
  memory.md                              ← auto-generated index table
  2026-03-02-kubernetes-pod-fix.md       ← individual memory
  2026-03-02-docker-port-change.md
```

Each file:

```markdown
---
title: "Kubernetes pod restart loop fix"
tags: [troubleshooting, kubernetes, homelab]
created: 2026-03-02T12:00:00Z
---

Full markdown content here...
```

### Browsing Memories

Read the index: `file_read ~/.netclaw/memories/memory.md`

This shows a table of all memories with date, title, tags, and relative file
links. Use `file_read` on individual files for full content.

### Tags

Use consistent tags to aid retrieval:

| Tag | Use For |
|-----|---------|
| `reference` | Factual knowledge, documentation |
| `how-to` | Procedures, step-by-step guides |
| `decision` | Architectural or design decisions |
| `troubleshooting` | Problems encountered and solutions |
| `coding-standard` | Conventions and patterns |
| `todo` | Items to follow up on later |

### Memory Quality

Write memories that are **self-contained and richly detailed**. A future agent
should understand them without the original conversation. Include: code blocks,
configuration snippets, command output, links, tables, step-by-step
instructions. The more context, the more useful on retrieval.

## Pre-Compaction Memory Extraction

During context compaction, the session actor automatically extracts important
context and saves it (tagged `extraction, compaction`). This is separate from
your explicit `store_memory` calls — both mechanisms work together to preserve
knowledge.

## Memory vs Identity Files

Identity files are **always loaded** into every system prompt. Memories are
**retrievable on demand** via search. Use the triage table in the
identity-management skill to decide where information belongs.

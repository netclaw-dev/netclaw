## Context

The hub auth framework (change: `hub-auth-framework`) provides `[Authorize]`
on the hub, the loopback authentication scheme, `NetclawClaimTypes`,
`ClaimsPrincipalMapper`, and `ConnectionIdentity` propagation. This change adds
the first remote authentication scheme: bearer tokens obtained via a device
pairing flow.

The trust chain is: loopback = root of trust → local operator approves pairing
→ remote client gets a bearer token → subsequent connections are authenticated.

## Goals / Non-Goals

**Goals:**

- Self-hosted operators can grant remote CLI access without an external IdP
- Pairing UX is familiar (similar to Bluetooth, VS Code tunnels)
- Tokens are long-lived but revocable
- Device registry provides visibility into who has access
- Startup fails if non-local exposure has no auth configured

**Non-Goals:**

- OIDC / Entra / OAuth integration (separate future scheme)
- Token rotation / expiry (V1 tokens are long-lived, revoke to invalidate)
- Web UI authentication flow (same bearer token mechanism, different UX later)
- Multi-tenant device management

## Decisions

### D1: Pairing code flow over a dedicated HTTP endpoint

The pairing exchange uses a dedicated REST endpoint (`POST /api/pair/exchange`)
rather than the SignalR hub. This endpoint is the ONLY unauthenticated endpoint
besides health probes. It accepts a pairing code and device name, returns a
device token if the code is valid.

**Why not the hub?** The hub has `[Authorize]` — an unpaired client can't
connect to it. The pairing endpoint is intentionally outside the auth gate,
scoped to a single operation with a time-limited code.

The endpoint is always registered but only functional when a pending pairing
code exists. Without a pending code, all exchange requests are rejected.

### D2: Token storage as salted SHA-256 hash

The device registry stores `SHA256(token + salt)`, not the raw token. The
raw token is shown once during pairing and stored only on the remote client's
machine in `secrets.json`. This follows the API key best practice — if
`devices.json` is compromised, tokens cannot be recovered.

Each device entry:
```json
{
  "name": "aaron-laptop",
  "tokenHash": "<sha256-hex>",
  "salt": "<random-hex>",
  "createdAt": "2026-04-01T...",
  "lastUsedAt": "2026-04-01T..."
}
```

### D3: Token format is a random 256-bit value, base64url-encoded

Token is 32 bytes of `RandomNumberGenerator` output, encoded as base64url
(no padding). This gives 256 bits of entropy — brute-forcing is infeasible.

No JWT, no structure, no expiry claim. The token is opaque to the client.
Validation is: hash the presented token, look up the hash in the registry.
Revocation is: delete the entry.

**Alternative considered**: JWT with expiry. Rejected because JWTs require
a signing key, add complexity (key rotation, clock skew), and the "revoke
by deleting the entry" model is simpler and sufficient for self-hosted
single-daemon deployments. JWT is the right choice for managed/multi-tenant
(that's the OIDC scheme).

### D4: Pairing code format and lifecycle

Code format: 8 alphanumeric characters, grouped as `XXXX-XXXX` for
readability. Characters from a reduced alphabet (no 0/O/1/I confusion):
`23456789ABCDEFGHJKLMNPQRSTUVWXYZ`.

Lifecycle:
- Generated by `netclaw daemon pair` (requires daemon running, command
  connects via SignalR as local operator)
- Stored in memory only (not persisted) with 5-minute TTL
- Single-use: consumed on successful exchange
- Only one pending code at a time (new code replaces previous)

### D5: `netclaw daemon pair` as a daemon-required CLI command

The `pair` subcommand connects to the running daemon via SignalR (as local
operator) and invokes a hub method `GeneratePairingCode()` that returns the
code. This ensures the code is generated inside the daemon process where it
can be validated during exchange.

The daemon logs the pairing code to stdout/logs as well, so Docker operators
can read it from container logs without needing a local CLI inside the
container.

### D6: `netclaw pair` as a standalone CLI command

The remote-side `netclaw pair <endpoint>` command:
1. Prompts for the pairing code
2. Prompts for a device name (defaults to hostname)
3. POSTs to `<endpoint>/api/pair/exchange` with code + device name
4. Receives the device token in the response
5. Stores the token in `~/.netclaw/config/secrets.json`
6. Stores the endpoint in `~/.netclaw/config/netclaw.json` as `Daemon:Endpoint`

This is an offline command — it does not require a local daemon.

### D7: CLI auto-attaches token for non-loopback endpoints

`DaemonClient`'s `HubConnectionBuilder` checks if the resolved endpoint is
non-loopback. If so, it reads `DeviceToken` from secrets and configures
`.WithUrl(url, options => options.AccessTokenProvider = ...)`.

If the endpoint is non-loopback and no token exists, the connection will fail
with 401. The CLI catches this and suggests running `netclaw pair`.

### D8: Startup validation extended for auth presence

The existing `ExposureModeValidationService` (from exposure-modes change) is
extended: after validating tunnel prerequisites, if the mode is non-local, it
checks whether at least one paired device exists in `devices.json` OR an
alternative auth scheme is registered. If neither, startup fails.

The check for "alternative auth scheme" is a simple interface —
`IRemoteAuthSchemeRegistration` — that any auth scheme (OIDC, etc.) can
register. The device pairing scheme registers itself. If no implementations
are registered and no devices exist, the check fails.

## Risks / Trade-offs

**[Pairing endpoint is unauthenticated]** → The endpoint only accepts a
time-limited, single-use code. Without a valid code, all requests are rejected.
Attack surface is minimal: brute-forcing an 8-character code from a 32-char
alphabet within 5 minutes requires ~1.1 trillion attempts. Rate limiting on
the endpoint adds defense in depth.

**[Token has no expiry]** → Tokens are valid until revoked. This is simpler
but means a compromised token grants access indefinitely until noticed.
Mitigation: `lastUsedAt` timestamps help operators identify stale devices.
Token rotation can be added later without changing the auth scheme.

**[devices.json is a flat file, not a database]** → For single-daemon
self-hosted deployments, the device count is small (typically <10). A JSON
file is sufficient. Locking uses the same file-write pattern as other config
files. Not suitable for multi-tenant — managed deployments use OIDC instead.

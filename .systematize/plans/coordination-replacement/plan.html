A completed child should be a tool result

A parent asks a child to inspect a log. The parent remains available. When the child finishes, the parent uses its evidence and answers.

The deployed stack routes that result through ordinary input admission and durable task selection. Each step adds state that another step must interpret.

Current path

Save child result
Prepare result
Save DeliveryAdmitted(InputAdmitted)
Queue SendUserMessage
Save ToolTaskAdopted
Build the tool call/result pair
Ask the parent model

Proposed path

Save child result
Prepare result
Tool workflow selects it at a safe boundary
Model context supplies the tool call/result pair
Save the parent's decision and consumption together

These steps are schematic. They omit normal authorization, serialization, and output steps. The replacement retains those checks.

Here, consumption means a saved parent decision records that it used the result. It does not mean the model provider receives exactly one request.

A crash can repeat a model request. It must not repeat uncertain child actions. Keep the child's original authority through later tools and approvals.

Recommendation: replace the runtime mechanisms on the refactored dev base. Retain the useful composition and cooperation skills.

Smaller alternative: repair the deployed stack and port it. That changes fewer contracts initially, but retains the duplicate input and task-selection paths.

Agreed behavior

Confirmed by the operator The operator approved these behaviors and authorized implementation of the replacement stack.

1. Return as soon as the task is safely accepted

Netclaw validates the request and saves the accepted child task. Then spawn_agent or the routed skill returns a run ID and accepted status.

The parent does not wait for the child to finish. A five-minute log inspection can continue while the parent answers another question.

Acceptance is not completion or a promise to resume uncertain child actions after a crash. A failed acceptance write starts no child.

This retains the deployed draft's contract. Current dev differs, so update its tool instructions and all routed adapters together.

2. Deliver each result when it is ready

If child A still needs result preparation, ready child B can reach the parent first. Do not enforce the order in which children finished.

Remove the terminal-order queue and its sequence checks where no other consumer requires them.

A result still waits for a safe parent boundary. It cannot interrupt an active model call or incomplete tool batch.

Ordinary user inputs retain their whole ordered batch. This rule orders user input; it does not impose child completion order.

Outcome and scope

One objective governs this replacement: useful cooperation with fewer independent states and fewer interactions between owners.

  • The parent receives completed child work without a reminder or another user message.
  • Status shows facts, including pending approvals and confirmed progress.
  • Cancellation, consent, recovery, and duplicate handling preserve the original authority.
  • Repeat-tool rules permit productive changes and reject proven recurrence.
  • Skills guide scoped delegation, artifact exchange, independent review, and evidence-based completion.
  • A retained large tool result suggests focused child inspection for the parent's question.

Excluded: a universal job framework, recursive child delegation, new child shell-job support, automatic context-window probing, provider configuration repairs, and an eval-runner rewrite.

Shell-job result roles need a separate contract. They remain outside this replacement. Do not attach a second result to the original submission call.

Issue #2453 remains a deployment gate. Its reminder route and failed-recovery notification need a bounded repair or verified resolution before rollout.

State and recovery rules
  • Acceptance commits before the child starts. A failed write produces zero child calls.
  • Cancellation intent survives restart. Live dispatch closes before cancellation reports completion.
  • Owner loss does not automatically restart uncertain child actions.
  • A saved terminal result permits preparation to retry without child execution.
  • A prepared result remains available until a correlated parent decision consumes it.
  • A decision that starts tools retains the child authority until those tools and approvals settle.
  • A compact closed-run identity rejects duplicate starts after transcript compaction.
  • Validation occurs before the journal write. Replay remains strict; it does not silently ignore invalid events.
  • Ordinary admitted inputs remain pending until ToolBatchStarted, TurnRecorded, or InputClosed consumes their identities.

The exact event fields and legacy translation remain design work. These rules constrain that work; they do not approve a finished wire schema.
